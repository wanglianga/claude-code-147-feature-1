# 云溪山居 · 乡村民宿旺季运营平台

面向乡村民宿旺季（节假日）的一体化运营平台：统一 **官网 / 小程序 / OTA / 电话** 四渠道的房态、价格、入住人数、宠物规则、儿童加床、早餐份数、押金与发票要求；把 **订单 → 保洁 → 布草 → 维修 → 早餐 → 事件 → 差评补偿 → 超卖换房补偿 → 结算** 放进同一条住宿链路；旺季结束后按渠道/房型/服务环节复盘利润，并据超卖（含合作民宿转住成本与渠道责任）、布草延迟、早餐投诉、补偿成本自动调整下一轮节假日的可售房量与渠道同步策略。

## 技术栈

- 前端：React 18 + Vite + Ant Design 5 + ECharts
- 后端：NestJS 10 + TypeORM（含 Swagger 文档 `/api/docs`）
- 数据库：PostgreSQL（开发用 15 验证，Compose 用 16）

## 一键启动（Docker Compose）

```bash
docker compose up --build
```

- 前端：http://localhost:8080
- 后端 API：http://localhost:3000/api （Swagger 文档：http://localhost:3000/api/docs）
- 首次启动自动建表并写入 **2026 国庆旺季（10-01~10-08，"今天"为 10-03）** 演示数据：12 间房、4 渠道、19 张订单、保洁/布草/维修/早餐记录、8 类履约事件、5 条评价与补偿记录、3 家同村合作民宿及其房源报价、2 起渠道超卖换房案件（1 起已按合作民宿转住结案、1 起 10-04 待处理）。

## 本地开发

```bash
# 1. 数据库（任一方式）
docker compose up -d db                                  # 用 Compose 起 Postgres(5432)
# 或使用本机已有 PostgreSQL，创建 homestay 库后通过 DATABASE_URL 指向它

# 2. 后端（首次启动自动建表+种子数据）
cd server && npm install
DATABASE_URL=postgres://homestay:homestay123@localhost:5432/homestay npm run start:dev

# 3. 前端（Vite 代理 /api → localhost:3000）
cd web && npm install && npm run dev                    # http://localhost:5173
```

## 演示动线（种子数据已埋好完整故事线）

1. **经营看板**：入住率/ADR/RevPAR、渠道收入分布、履约事件分布、差评归因四象限（硬件/服务/超卖/餐食）。
2. **房态日历**：房间×日期占用与价格；下方库存表可见 10-01 庭院双床房、10-04 山景大床房两处**超卖**红色告警。
3. **订单管理**：新建订单会统一校验宠物/加床/人数规则与库存（OTA 可强制下单并触发超卖事件）；订单详情抽屉含 **链路事件 / 保洁 / 评价补偿 / 结算明细** 五个页签。可现场操作：入住 → 临时加人（早餐费自动重算）→ 延迟退房（自动生成事件+保洁任务）。
4. **保洁与布草**：「智能排班」按下一单入住时间、脏污程度、维修冲突、布草库存自动派单（301 房有空调维修告警）；完成打扫扣减布草；送洗签收超时 2 小时自动记布草延迟事件。
5. **早餐备餐**：按在住人数与忌口（不吃辣/素食/海鲜过敏）自动汇总需求；确认备餐量不足即生成早餐供应不足事件。
6. **事件与差评**：差评（≤3 分）自动进入链路；对差评发放现金/退款/补偿券（自动生券码），补偿后差评事件自动关闭；补偿券可核销。
7. **超卖换房补偿**（「超卖换房补偿」页）：OTA 延迟同步致同一间景观房被两位客人预订时，按房型+入住日「检测超卖」建案件；平台依据**下单时间/到店时间/订单价值/会员等级**给冲突客人评分，前 N 名保留原房，其余客人由管家安排**升级房 / 同村合作民宿转住 / 退款补偿**，客人接受/拒绝均可记录（拒绝可重新出方案）。接受后：原订单保留超卖原因、渠道责任（`ota_delayed_sync`）与补偿成本；转住时记录**合作方价格、距离、客人满意度、结算方式（月结/逐晚现结/平台预付）**并占用合作房量，订单结算口径改为合作方价、**渠道不再按原房型结算（佣金置 0 并给出防错提示）**。种子已埋两起案件：10-01 吴女士转住竹溪民宿（已结案、满意度 3 分）与 10-04 山景大床房 4 人冲突（谢女士待处理，可现场走一遍流程）；页内「超卖复盘」汇总渠道责任与成本，「渠道同步策略」供店主复盘时收紧推送间隔、预留安全缓冲、改为人工确认放房。
8. **结算中心**：每笔订单的房费、加床、早餐、宠物费、渠道佣金（OTA 15%）、赔付补偿、押金扣留/退还、净收入逐行列清；转住订单显示「合作方价结算」口径与合作民宿代收/代付行。
9. **旺季复盘**：分渠道/分房型利润表、服务环节收入 vs 成本、问题自动归类（价格策略问题/履约能力问题/个别客诉）、超卖复盘（渠道责任、换房方式效果、合作方价格/距离/满意度/结算方式）；最下方给出下一轮节假日各房型**建议可售房量**（本例中山景大床房因超卖+布草+早餐+补偿综合下调 3→2），选择日期区间后「应用到下一轮节假日」即写入库存。

## 验证方式（实际执行过的验证）

本仓库交付前在 Linux + PostgreSQL 15 + Node 22 环境实际执行：

```bash
# 后端编译
cd server && npx tsc -p tsconfig.build.json

# 端到端 API 验证（85 项断言全部通过）
python3 scripts/verify.py
```

`scripts/verify.py` 覆盖：登录鉴权、禁宠/加床/人数规则拒绝、库存不足 409、OTA 强制下单触发超卖事件、临时加人费用重算、延迟退房事件、退房生成保洁任务、智能排班（含维修冲突告警）、保洁完成扣减布草、布草延迟事件、早餐需求汇总与不足事件、差评自动入链、补偿券发放与核销、结算净额勾稽、OTA 15% 佣金校验（转住单除外）、复盘三分类、调价建议与库存应用，以及**超卖换房补偿全链路**：四因子评分与优先保留、重复检测幂等、合作方价/距离/结算方式展示、转住接受后释放原房型并占用合作房量、原订单保留超卖原因与渠道责任、转住单按合作方价结算（佣金 0 + 防错提示）、转住回访满意度、升级房差价吸收、退款补偿落账并取消订单、客人拒绝后重新提案、店主收紧同步策略、超卖复盘统计。

前端通过 `npm run build` 构建，并以 `vite preview` 验证页面、静态资源与 `/api` 代理连通（登录接口 200）。
