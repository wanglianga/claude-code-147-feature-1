# 云溪山居 · 乡村民宿旺季运营平台

面向乡村民宿旺季（节假日）的一体化运营平台：统一 **官网 / 小程序 / OTA / 电话** 四渠道的房态、价格、入住人数、宠物规则、儿童加床、早餐份数、押金与发票要求；把 **订单 → 保洁 → 布草 → 维修 → 早餐 → 事件 → 差评补偿 → 超卖换房补偿（店内升级/同村合作民宿转住/退款）→ 结算** 放进同一条住宿链路；旺季结束后按渠道/房型/服务环节复盘利润，并据超卖、布草延迟、早餐投诉、补偿成本自动调整下一轮节假日的可售房量与渠道同步策略。

## 技术栈

- 前端：React 18 + Vite + Ant Design 5 + ECharts
- 后端：NestJS 10 + TypeORM（含 Swagger 文档 `/api/docs`）
- 数据库：PostgreSQL（开发用 15 验证，Compose 用 16）

## 一键启动（Docker Compose）

```bash
docker compose up --build
```

- 前端：http://localhost:8080
- 后端 API：http://localhost:3000/api （Swagger 文档：http://localhost:3000/api/docs）
- 首次启动自动建表并写入 **2026 国庆旺季（10-01~10-08，"今天"为 10-03）** 演示数据：12 间房、4 渠道、19 张订单、保洁/布草/维修/早餐记录、8 类履约事件、5 条评价与补偿记录、2 家同村合作民宿、4 渠道房态同步策略、2 张超卖换房补偿工单（1 张已转住结案、1 张待处置）。

## 本地开发

```bash
# 1. 数据库（任一方式）
docker compose up -d db                                  # 用 Compose 起 Postgres(5432)
# 或使用本机已有 PostgreSQL，创建 homestay 库后通过 DATABASE_URL 指向它

# 2. 后端（首次启动自动建表+种子数据）
cd server && npm install
DATABASE_URL=postgres://homestay:homestay123@localhost:5432/homestay npm run start:dev

# 3. 前端（Vite 代理 /api → localhost:3000）
cd web && npm install && npm run dev                    # http://localhost:5173
```

## 演示动线（种子数据已埋好完整故事线）

1. **经营看板**：入住率/ADR/RevPAR、渠道收入分布、履约事件分布、差评归因四象限（硬件/服务/超卖/餐食）。
2. **房态日历**：房间×日期占用与价格；下方库存表可见 10-01 庭院双床房、10-04 山景大床房两处**超卖**红色告警。
3. **订单管理**：新建订单会统一校验宠物/加床/人数规则与库存（OTA 可强制下单并触发超卖事件）；订单详情抽屉含 **链路事件 / 保洁 / 评价补偿 / 结算明细** 五个页签。可现场操作：入住 → 临时加人（早餐费自动重算）→ 延迟退房（自动生成事件+保洁任务）。
4. **保洁与布草**：「智能排班」按下一单入住时间、脏污程度、维修冲突、布草库存自动派单（301 房有空调维修告警）；完成打扫扣减布草；送洗签收超时 2 小时自动记布草延迟事件。
5. **早餐备餐**：按在住人数与忌口（不吃辣/素食/海鲜过敏）自动汇总需求；确认备餐量不足即生成早餐供应不足事件。
6. **事件与差评**：差评（≤3 分）自动进入链路；对差评发放现金/退款/补偿券（自动生券码），补偿后差评事件自动关闭；补偿券可核销。
7. **超卖换房补偿**（菜单项）：OTA 延迟同步同房被两渠道预订后，可从超卖事件一键生成处置工单——平台按**下单时间、到店时间、房型价值、会员等级**四因子组内打分（因子分明细可查），同房另一单优先保留原房；管家安排三种方案：
   - **店内升级房**：选择当晚更高价值的物理空房（如山景大床→Loft 观景套房），房型差价平台承担并可叠加补偿券；接受后自动换房、原房型库存回落、新房型占用 +1，订单保留原房型用于渠道结算；
   - **同村合作民宿转住**：记录合作方**合作价、距离、结算方式（月结/预付/客人自付）**，接受后订单转 `relocated`、本店库存释放、房态与早餐不再计入；结算口径锁定为合作价，**防止后续渠道仍按原房型结算**；
   - **退款补偿**：全额退款、押金退还、库存释放，退款单不进结算收入。
   每种方案都记录**超卖原因、补偿成本、渠道责任（全责/共担/平台承担）与渠道索赔**（索赔到账计入订单净额，渠道全责下净额回到应收水平），接受后记录**客人满意度（1-5）**。页面另含合作民宿台账、渠道同步策略调整（同步频率/缓冲房/即时推送）与超卖复盘（分渠道责任与索赔、合作方价格距离满意度结算评估）。种子故事：10-01 电话客人吴女士因 OTA 延迟同步受害，已转住「竹溪小院」结案（OTA 索赔 ¥880 到账）；10-04 曹先生（更早下单）与谢女士（铂金、到店更早）的 101 房冲突工单待现场处置。
8. **结算中心**：每笔订单的房费、加床、早餐、宠物费、渠道佣金（OTA 15%）、赔付补偿、合作民宿房费支出、超卖索赔到账、押金扣留/退还、净收入逐行列清；转住单带合作方标识，退款单不出现。
9. **旺季复盘**：分渠道/分房型利润表、服务环节收入 vs 成本（含合作民宿房费、渠道索赔冲减）、问题自动归类（价格策略问题/履约能力问题/个别客诉）；超卖处置页可直接收紧 OTA 同步策略（60 分钟→10 分钟 +1 间缓冲房）；最下方给出下一轮节假日各房型**建议可售房量**（本例中山景大床房因超卖+布草+早餐+补偿综合下调 3→2），选择日期区间后「应用到下一轮节假日」即写入库存。

## 验证方式（实际执行过的验证）

本仓库交付前在 Linux + PostgreSQL 15 + Node 22 环境实际执行：

```bash
# 后端编译
cd server && npx tsc -p tsconfig.build.json

# 端到端 API 验证（99 项断言全部通过）
python3 scripts/verify.py
```

`scripts/verify.py` 覆盖：登录鉴权、禁宠/加床/人数规则拒绝、库存不足 409、OTA 强制下单触发超卖事件、临时加人费用重算、延迟退房事件、退房生成保洁任务、智能排班（含维修冲突告警）、保洁完成扣减布草、布草延迟事件、早餐需求汇总与不足事件、差评自动入链、补偿券发放与核销、结算净额勾稽、OTA 15% 佣金校验、复盘三分类、调价建议与库存应用，以及**超卖换房补偿全链路**：四因子组内打分与同房保留规则、历史转住工单（合作价/距离/月结/满意度/责任渠道≠下单渠道/索赔到账）、升级方案（差价平台承担+补偿券、库存双向迁移、原房型保留结算、索赔到账后净额回到应收）、合作民宿转住（订单挂钩合作方、合作价结算锁定、双方共担索赔减半、库存与房态/早餐释放）、全额退款（押金退还且不进结算）、同步策略收紧、超卖复盘分渠道责任/索赔/合作方评估。

前端通过 `npm run build` 构建，并以 `vite preview` 验证页面、静态资源与 `/api` 代理连通（登录接口 200）。
